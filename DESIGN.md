# sqlx-query-v2 — design spec

This is the settled design from a design conversation, written down so a
fresh implementation session has full context without the conversation
history. Read this whole file before writing code — the "why" sections
matter as much as the signatures; several shapes here look more elaborate
than the obvious alternative on purpose, and the rationale says why.

## Motivation

The originating problem: [grpc-rust-template](https://github.com/protoc-contrib/grpc-rust-template)
has `List` RPC handlers (`list_collections`, `list_items`) that need to
turn a client-supplied AIP-160 `filter` (CEL) and AIP-132 `order_by`
string into SQL, safely, against a fail-closed column allow-list. The
base queries are generated by [sqlc-gen-sqlx](https://github.com/mathematic-inc/sqlc-gen-sqlx)
from hand-written `.sql` files that already carry sentinel comments
anticipating exactly this:

```sql
SELECT * FROM collection
WHERE /* query.where AND */ TRUE
ORDER BY /* query.order_by , */ collection_id
LIMIT $1 OFFSET $2
```

`sqlc-gen-sqlx` emits that text **verbatim** into a `const SQL: &str` — it
has no idea the comments mean anything. Something at request time has to
find those markers and splice in real SQL, safely, with placeholders
numbered correctly relative to whatever the base query already uses
(`$1`/`$2` for `take`/`skip` above).

## Prior art this is a port of

**[pgx-contrib/pgxquery](https://github.com/pgx-contrib/pgxquery)** (Go) solves exactly this problem, and is the
reference implementation for the splicing mechanism. Read `rewriter.go`
before implementing the composer. Key points:

- Sentinel regex matches `/* <connective> query.<name> <suffix> */` and
  captures the connective/separator so it's preserved verbatim. **Note:**
  pgxquery's own convention is connective-first (`/* AND query.where */`).
  The grpc-rust-template SQL above is **name-first**
  (`/* query.where AND */`, `/* query.order_by , */`). Match the
  name-first convention — it's what the actual target SQL uses — which
  simplifies the regex since there's no leading connective to capture:
  `/\*\s*\bquery\.(\w+)\b([^*]*?)\s*\*/` (capture group 1 = name, group 2 =
  trailing connective/separator, preserved as-is).
- **Placeholder numbering is index-based, not text-order-based.** This
  was the thing that looked like a blocker and isn't: Postgres resolves
  `$N` by position in the flat bind-argument list, not by where it's
  written in the SQL text. So a fragment's `$1`, `$2`, ... (numbered
  locally, as if it were the only thing in the query) just needs shifting
  to `$(1+offset)`, `$(2+offset)`, ... where `offset` is a plain integer —
  how many bind values already exist before this fragment — not something
  that requires scanning the rest of the query text.
- **`shiftPlaceholders`** is the part worth porting faithfully and testing
  hard: a character-by-character scanner over the fragment text that skips
  single-quoted strings, double-quoted identifiers, dollar-quoted bodies,
  line comments, and nested block comments, and rewrites only the `$N`s
  that are live SQL. Getting this wrong is the one way this design could
  produce subtly wrong SQL. Port the test fixtures too (`fake/*.sql` in
  pgxquery).
- pgx has a `pgx.QueryRewriter` interface that gets invoked automatically
  when passed as a bind arg — **sqlx has no equivalent hook.** This crate
  needs an explicit builder (`QueryComposer`) doing at `build()` time what
  `RewriteQuery` does automatically in Go.

**Also relevant, already built, do not duplicate their logic:**

- [`sqlx-cel`](https://github.com/sqlx-contrib/sqlx-cel) — CEL → SQL `WHERE` fragment + bind values, working, uses
  `cel`'s `chrono` feature narrowly (only to constant-fold closed literal
  subtrees like `timestamp('...') - duration('24h')` into one bind value —
  not general evaluation; `matches()` is deliberately left un-folded and
  lowered to the dialect's own regex operator since it always has a column
  on one side and can't fold).
- [`sqlx-aip`](https://github.com/sqlx-contrib/sqlx-aip) — AIP `filter`/`order_by`/`page_token` → fragments, built on
  `sqlx-cel`. Currently pulled from the org (local-only). Its logic
  (keyset cursor tuple-comparison building, `OrderBy` → column resolution)
  is not being thrown away — it's being folded into this crate's `OrderBy`
  and (later) `Cursor`, decoupled from AIP-specific types, because none of
  it actually needs to know about AIP — it only needs a plain string and a
  column map, same as `Filter` does.

## Repo layout

**Monorepo, one repo (`sqlx-query-v2`), workspace with a `crates/` dir:**

```
sqlx-query-v2/
├── Cargo.toml                  # [workspace], members = ["crates/*"]
└── crates/
    ├── sqlx-query-v2/          # the base crate — see below
    └── sqlx-query-cel/         # depends on sqlx-query-v2
```

Do not split these into separate repos. Do not add a third crate for
`Value`/`QueryFragment`/`QueryResolver` — they live in `sqlx-query-v2`.

## Dependency direction (important, avoids a cycle)

`sqlx-query-cel` depends on `sqlx-query-v2`, **never the reverse.**
`sqlx-query-v2` defines `Value`, `QueryFragment`, `QueryResolver` and
knows nothing about CEL. `sqlx-query-cel` implements those traits for its
`Filter` type. This is the same shape as `sqlx-aip` depending on
`sqlx-cel` today — the more domain-specific crate depends on the more
foundational one.

## Public API

```rust
// =====================================================================
// crates/sqlx-query-v2 — the base crate.
// =====================================================================

pub enum Value {
    Null,
    Bool(bool),
    Int(i64),
    Float(f64),
    String(String),
    Timestamp(chrono::DateTime<chrono::Utc>),
}

/// The one thing QueryComposer depends on: render to SQL text + the
/// values it binds. Filter and OrderBy both implement this directly —
/// there is no separate "resolved" wrapper type (see Decisions below).
pub trait QueryFragment {
    fn into_sql(self) -> (String, Vec<Value>);
}

/// Renames field names to columns against a fail-closed allow-list.
/// Separate from QueryFragment on purpose — resolving and rendering are
/// different steps, and not every fragment needs an allow-list.
pub trait QueryResolver: Sized {
    type Error;
    fn resolve(self, columns: &HashMap<&str, &str>) -> Result<Self, Self::Error>;
}

/// A parsed `order_by` value: "field [asc|desc], ...". No CEL involved.
pub struct OrderBy { /* .. */ }
pub enum OrderByError { /* .. */ }

impl OrderBy {
    pub fn parse(order_by: &str) -> Result<Self, OrderByError>;
}
impl QueryResolver for OrderBy {
    type Error = OrderByError;
    fn resolve(self, columns: &HashMap<&str, &str>) -> Result<Self, Self::Error>;
}
impl QueryFragment for OrderBy {
    fn into_sql(self) -> (String, Vec<Value>) { (self.render(), Vec::new()) }
}

/// Names the driver and whether it's $N or ?-numbered, which the
/// sentinel placeholder-shift logic needs.
pub trait QueryDialect: sqlx::Database {
    fn positional(&self) -> bool;
}

/// Splices QueryFragments into `/* query.<name> */` sentinel comments in
/// a static SQL template — the pgx-contrib/pgxquery port. `sql` is never
/// parsed structurally, only scanned once for its own placeholder count.
pub struct QueryComposer<DB: QueryDialect> { /* .. */ }

impl<DB: QueryDialect> QueryComposer<DB> {
    pub fn new(sql: &'static str) -> Self;

    /// A value for one of the base query's own placeholders, filled in
    /// declaration order.
    pub fn bind(&mut self, value: impl Into<Value>) -> &mut Self;

    /// Splices onto `/* query.where */`.
    pub fn filter(&mut self, fragment: impl QueryFragment) -> &mut Self;

    /// Splices onto `/* query.order_by */`.
    pub fn order_by(&mut self, fragment: impl QueryFragment) -> &mut Self;

    pub fn build(&self) -> Result<sqlx::query::Query<'static, DB, DB::Arguments>, Error>;
}

// =====================================================================
// crates/sqlx-query-cel — depends on sqlx-query-v2.
// =====================================================================

pub struct Filter { /* .. */ }
pub enum FilterError { /* .. */ }

impl Filter {
    pub fn parse(cel: &str) -> Result<Self, FilterError>;
}
impl sqlx_query_v2::QueryResolver for Filter {
    type Error = FilterError;
    fn resolve(self, columns: &HashMap<&str, &str>) -> Result<Self, Self::Error>;
}
impl sqlx_query_v2::QueryFragment for Filter {
    fn into_sql(self) -> (String, Vec<sqlx_query_v2::Value>);
}
```

### Usage (target shape)

```rust
use sqlx_query_v2::{OrderBy, QueryComposer};
use sqlx_query_cel::Filter;

let columns = HashMap::from([
    ("status",  "status"),
    ("rank",    "rank"),
    ("created", "created_at"),
    ("id",      "collection_id"),
]);

let filter   = Filter::parse(&request.filter)?.resolve(&columns)?;
let order_by = OrderBy::parse(&request.order_by)?.resolve(&columns)?;

let mut query = QueryComposer::<Postgres>::new(pg::LIST_COLLECTIONS_SQL);
query
    .bind(take)
    .bind(skip)
    .filter(filter)
    .order_by(order_by);

let rows = query.build()?.fetch_all(&pool).await?;
```

## Decisions and why (read before deviating)

- **Marker-splice, not `sqlparser` AST rewriting.** The predecessor crate
  (`sqlx-contrib/sqlx-query`) parses the whole base query with `sqlparser`
  and rewrites the AST. That's more general (works on arbitrary SQL) but
  costs a real dependency, a dialect-completeness risk (a query the driver
  accepts might fail to parse), a full-AST clone on every render, and no
  way to cheaply reuse a parsed base query across requests. Every query
  this crate will ever actually see comes from `sqlc-gen-sqlx` already
  shaped with sentinel markers, so that generality isn't exercised. Match
  the ecosystem's own precedent (`pgxquery`) instead of reinventing a
  structurally different approach.
- **No `sqlparser` dependency at all.** Because the base SQL is never
  parsed structurally — only scanned for its own sentinel comments and
  placeholder count — it can contain any syntax the target driver accepts.
- **`Filter`/`OrderBy` implement `QueryFragment` directly — no
  `Resolved<T>` wrapper.** An earlier iteration of this design used a
  wrapper type so that only a *resolved* fragment could satisfy
  `QueryFragment`, making it a compile error to push an unresolved
  (unchecked-field-names) fragment into the composer. That's real
  protection — an unresolved `Filter` holds whatever field names a client
  wrote in CEL, and the CEL environment generated from a proto declares
  *every* field of the resource, so `internal_notes == "x"` parses fine
  until something checks it against the allow-list. The wrapper was
  deliberately dropped in favor of the simpler direct-`impl` shape above.
  **This means calling `.resolve()` before pushing to the composer is
  discipline, not compiler-enforced — treat this as the one place in the
  API where forgetting a call is a silent security bug, not a compile
  error, and write tests accordingly.**
- **`resolve()` consumes `self`, returns `Self` — no internal clone.**
  Matches the predecessor crate's `OrderBy::resolve`/`Filter::resolve`.
  There's no case in this design that needs resolving the same fragment
  against two different column maps.
- **`QueryResolver` has an associated `Error` type**, so `Filter`'s errors
  (CEL syntax, unknown field) and `OrderBy`'s errors (bad direction,
  unknown field) don't have to share one enum.
- **`QueryFragment`/`QueryResolver` are prefixed** (not bare `Fragment`/
  `Resolver`) to avoid collision with the extremely common `Resolver`
  name (DNS/dependency/GraphQL resolvers) and for consistency with
  `QueryComposer`/`QueryDialect`.
- **`OrderBy`, not `Order` or `Sort`.** Every sibling crate already uses
  this name — `aip::OrderBy` in `aip-rs`, `aip.OrderBy` in `pgxaip` (Go),
  and the predecessor `sqlx-query` crate itself. Don't introduce a third
  name for the same concept.
- **`sqlx-aip` is not being deleted, its logic is being absorbed.** Once
  `OrderBy` is generic (not AIP-specific) and a future `Cursor` fragment
  can be built the same way, there's no AIP-specific glue left that needs
  its own crate — the AIP-specific *request types* stay in `aip-rs`/
  generated code, this layer only ever sees plain strings and a column
  map.

## Explicitly out of scope for the first implementation pass

- **Cursor / keyset pagination.** Not designed yet. When it happens, it
  should be a fragment type living in `sqlx-query-v2` (no CEL needed)
  implementing both `QueryFragment` and `QueryResolver` the same way
  `OrderBy` does — likely modeled on `sqlx-aip`'s `cursor.rs` /
  `pgxaip`'s `rewriteCursor` (the OR-of-ANDs tuple comparison), but
  producing a plain fragment instead of AIP-specific types.
- Building a `SELECT` from scratch. This crate only ever splices into a
  base query the caller already wrote.
- Deciding `LIMIT`/`OFFSET`. Stays the caller's problem, same as
  `sqlx-aip`'s stated scope.

## Testing expectations

- Port `pgxquery`'s `fake/*.sql` fixtures and the `shiftPlaceholders`
  edge cases (placeholders inside string literals, quoted identifiers,
  dollar-quoted bodies, line comments, nested block comments) faithfully
  — this is the highest-risk piece of logic in the whole crate.
  If you can find them - they should be under `github.com/pgx-contrib/pgxquery/tree/main/fake`, but if not you can find them under `github.com/pgx-contrib` org.
- End-to-end composer tests against SQL shaped like the real target
  queries: `WHERE /* query.where AND */ TRUE`, `ORDER BY
  /* query.order_by , */ collection_id`, followed by `LIMIT $1 OFFSET $2`
  — i.e. a marker with caller-numbered placeholders *after* it in the
  text, to prove the index-based (not text-order-based) numbering
  actually works end to end, not just in the fragment-shifting unit.
